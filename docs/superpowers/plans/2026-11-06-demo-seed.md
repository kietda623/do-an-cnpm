# T150 Demo Seed Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a repeatable `seed:demo` command that creates 10 demo shops, 1,000 demo products, and deterministic account/order/payment/shipping fixtures on a confirmed disposable PostgreSQL database without resetting existing transaction or inventory state.

**Architecture:** Keep the current US/test seed scripts unchanged. Put deterministic fixture planning and environment validation in small pure modules; have the guarded `demo.seed.ts` entry point call an exported database seeder. Use stable IDs/keys and create-only writes for transaction and inventory rows, with inventory movements and balances committed atomically.

**Tech Stack:** TypeScript, Node.js built-in `node:crypto`, Prisma 7.10.1, PostgreSQL via `@prisma/adapter-pg`, `argon2`, Jest 30.

**Spec:** `docs/superpowers/specs/2026-11-06-demo-seed-design.md`; task T150 in `specs/001-marketplace-mvp/tasks.md`.

## Global Constraints

- `seed:demo` accepts only `TEST_DATABASE_URL` with PostgreSQL protocol, a database suffix `_test` or `_disposable`, and exact `TEST_DATABASE_NAME_CONFIRMATION`; never fallback to `DATABASE_URL`.
- Never reset, truncate, delete, or migrate the target database from the seed command.
- Secrets are required through `DEMO_SELLER_PASSWORD`, `DEMO_BUYER_PASSWORD`, and `DEMO_LOCKED_BUYER_PASSWORD`; no defaults, committed secrets, or secret/hash logging.
- Create exactly 10 demo shops × 100 demo products; counts refer to seed-owned stable keys and do not assume the database contains no unrelated records.
- Keep existing fixture seed scripts and schema/migrations unchanged.
- Existing order/payment/refund/shipment state and inventory balance must survive a second seed run unchanged.
- T150 depends on T149. Do not tick T150 while T149 remains open.

## Review Focus

- Wrong or missing database confirmation must fail before any connection; test valid PostgreSQL, wrong suffix, wrong confirmation, invalid URL/protocol, and absent `TEST_DATABASE_URL` without a `DATABASE_URL` fallback.
- Deterministic IDs and natural keys must remain stable and unique across 10 shops, 1,000 products, and all four orders; assert repeat equality and cardinalities.
- Re-running the seed must not reset an existing order/payment version, inventory adjustment, status, allocation, or refund; integration test changes a disposable fixture after the first run and checks the second run preserves it.
- Inventory movement operation keys and `(orderItemId, effectType)` must not collide; assert explicit `SALE`/`RESTORE` effect types and ledger-derived `availableQuantity`.
- Missing or out-of-policy bootstrap passwords must fail without logging credentials; test configuration rejection and inspect captured output for secret absence.
