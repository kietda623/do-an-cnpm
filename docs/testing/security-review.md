# T146 Security Review

**Review date:** 2026-11-10
**Scope:** API mutation authorization and the security controls named in T146.
**Result:** No unguarded protected mutation was found in the reviewed route inventory. One log-redaction issue was reproduced and fixed. Database-backed checks still need the dedicated disposable test database; Redis integration checks need the local test Redis service.

## Mutation authorization inventory

The controller source contains 48 `POST`, `PATCH`, `PUT`, or `DELETE` routes. Three are public credential/token flows by design: register, login, and refresh. The other 45 require a Bearer access token. `tests/security/authorization.spec.ts` loads the API suite that probes all 45 protected routes without credentials; each must return `401` before payload validation or persistence. The suite passed locally in the unit-test mode with persistence mocked.

The protected routes cover account/profile/address/media changes; shop creation and moderation; category, product, variant, and inventory changes; cart, quote, checkout, payment, order, fulfillment, shipment, and review writes; and administrator user/product/return/order operations. Administrator endpoints also apply `AdminGuard`. Object-level authorization remains in the corresponding services and uses the authenticated user ID and current shop membership.

## Controls reviewed

- **IDOR and role boundaries:** User profile and address operations derive the user ID from the access context. Shop-scoped writes resolve active membership from persistence. Buyer/seller order operations scope reads and mutations by the corresponding buyer, shop, or admin actor. Existing negative integration cases cover foreign shop logos/assets, cross-shop product and fulfillment writes, another buyer's cart/review, and buyer attempts at admin actions. The new address case asserts another buyer cannot list, update, or delete the owner's address and that the owner's row remains unchanged.
- **CSRF and CORS:** Credentialed CORS uses the configured browser-origin allowlist. Browser auth mutations require an allowed `Origin` and a signed double-submit CSRF token. Other writes require a Bearer token and ignore unrelated/stale browser cookies. `apps/api/test/http/cors-csrf.spec.ts` covers preflight, blocked origins, readable CSRF rejection, stale-cookie handling, and a valid token.
- **Rate limiting:** Current per-minute defaults are register IP 60, login IP 180, and refresh IP 300; the email limits are 5/10 and refresh-family is 30. HMAC-derived keys avoid storing raw email/IP values in Redis keys. Redis uses one atomic Lua counter shared by app instances; service failures fail closed with `503`.
- **Uploads:** The API and service cap files at 5 MiB, accept JPEG/PNG/WebP only after signature detection, decode with Sharp and a 40-million-pixel limit, and remove partially written files after persistence failures. Product-image uploads require active shop membership. Local reads serve only verified assets whose resolved paths stay under the configured asset directory; production without S3 is unavailable.
- **Refresh reuse:** Refresh rotates tokens, rejects replay, revokes the token family on reuse, and logout revokes the current session. Browser cookie refresh/logout also pass through CSRF checks.
- **Secret and PII redaction:** Structured sensitive keys and text values are redacted, including bearer credentials, passwords, refresh tokens, API keys, database URI credentials, email, and phone values. The request logger records request metadata rather than request bodies.
- **Input handling:** Global DTO validation rejects malformed write payloads; data access uses Prisma parameterized queries. This review is scoped to the T146 risks and is not a formal OWASP ASVS certification.

## Finding fixed

The phone-number expression treated a numeric UUID as a phone number and replaced it in request paths and request IDs. That reduced log correlation. The redaction pattern now recognizes UUID-shaped values before matching phone numbers; phone values remain redacted. `apps/api/test/logger.spec.ts` verifies both behaviors along with credential/PII removal.

## Local integration prerequisites

Run the database-backed authorization, IDOR, and refresh-reuse cases with a dedicated PostgreSQL database whose name ends in `_test` or `_disposable`, and set `TEST_DATABASE_NAME_CONFIRMATION` to that exact database name. The test helper resets this database. The Redis integration suite uses `RATE_LIMIT_REDIS_URL` (default `redis://127.0.0.1:56380`) and only writes keys under a unique test prefix. Keep these test endpoints separate from application data and Redis Cloud production/demo data.
